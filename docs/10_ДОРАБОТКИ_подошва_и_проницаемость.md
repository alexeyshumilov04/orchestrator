# Доработки по замечаниям заказчика: подошва (U1_bot) и проницаемость (PERM)

Замечания получены по снимкам из GUI (проект `models/S001/Герасимовское.snp`):

1. **Подошва `U1_bot` построена нефизично** — «бычьи глаза»: поверхность жёстко
   подсажена на каждую скважину, вместо единой структуры получились локальные «куполки».
   Кровля `U1_top` при этом корректна.
2. **Пласт непроницаем** — на карте `PERM` значения почти всюду в районе `0.0001` мД при
   легенде до `34.6` мД: свойство распределено нефизично (не связано с пористостью и
   петрофизическими зависимостями).

Требование заказчика по обоим пунктам: **исправить и добавить проверки QA/QC, без хардкода**
(правило 1: пороги, методы, зависимости — только в данных).

## Текущая реализация (факты из проектного графа `ontology_project/gerasimovskoe.yaml`)

**Подошва.** Строки 241–247: *«ПОДОШВА U1_bot строится НЕЗАВИСИМО по маркеру J2 (как кровля
по BAJ), чтобы толщина считалась КОРРЕКТНО как “кровля − подошва”»* — то есть обе поверхности
идут отдельными шагами `horizon_interpolate_by_marker_idw` (кровля — с сейсмическим трендом,
подошва — без тренда). Именно поэтому подошва «подсаживается» на каждую скважину и даёт
«бычьи глаза». Рядом (строка 268) уже зафиксирован альтернативный маршрут:
*«…толщины строится ПОДОШВА (horizon_calculator → U1_bot)»* — то есть заготовка решения есть.
Толщина сейчас считается как `horizon("U1_top") − horizon("U1_bot")` (строка 286).

**Проницаемость.** Строки 79–80: соответствие мнемоник LAS → blocked well → куб:
`{log: "KINT", blocked: "Perm", cube: "PERM"}`, далее этап 7 интерполирует это на сетку
(`grid_property_interpolate_by_wells_log_3d`). **Петрофизической связи `PERM = f(PORO)` в данных
нет вообще** — проницаемость берётся напрямую из ГИС-канала. Порог физичности
`thresholds.perm: [0.1, 5000.0]` (строка 62) существует и ранее проходил (`PERM mean = 0.67`),
но это средняя по кубу: карта почти всюду показывает `0.0001` мД, то есть распределение
вырождено (фон ≈0 при локальных всплесках у скважин). Нужны свидетельства `property_stats`
(`count`/доля непустых/min/max/mean/уникальные значения), чтобы отличить «нет данных»
(правило 6) от «данные есть, но нефизичны».



## ОПРОВЕРГНУТО И ИСПРАВЛЕНО (раунд 81): каналы ГИС на месте, ошибка была в МОЁМ разборе LAS

**Правильные факты (чтение секции `~Curve` исходных LAS):**

```
КРИВАЯ: KINT.   : Permeability
КРИВАЯ: PHIE.   : Porosity factor
```

То есть мнемоники кривых — **`PHIE`** и **`KINT`** (именно их и запрашивает проектный
граф, и это верно), а слова `POROSITY`/`SATURATION`/`CLAY`/`LITHOLOGY` — **описания** в
заголовке, которые мой первый парсер ошибочно принял за имена кривых. Мой вывод раунда 79
(«запрошенных каналов нет в данных») **неверен и отменён**.

**Подтверждение живым прогоном:** подмена `PHIE` → `POROSITY` в данных привела к падению
(`item 5 "Create Blocked Wells by Well Log"`: `cannot find object "Well Log "POROSITY""`),
то есть в проекте существуют именно `PHIE`/`KINT`. Правка откачена, дерево зелёное.

**Что из этого следует для «непроницаемого пласта»:** кубы `PORO`/`PERM` строятся из
РЕАЛЬНЫХ кривых, поэтому причина не в отсутствии данных. Проверять нужно **единицы и
распределение** кривых: `PHIE` описан как «Porosity factor» (возможно, доли или проценты),
`KINT` — «Permeability» (мД?). Наблюдаемые карты: PORO медиана 0.049, PERM медиана 0.667 мД —
либо таковы исходные кривые, либо на импорте/апскейлинге теряется масштаб.



**Факты (чтение исходных LAS):**

* `data/Герасимовское/Source/RIGIS/*.las` (61 файл) — фактические кривые:
  `DEPTH, A, WATER, CLAY, POROSITY, SATURATION, LITHOLOGY, TIP`.
  **Ни `PHIE`, ни `KINT` в файлах нет** (пример строки данных:
  `2497.900  0.160  4.140  0.100  1.000  0.240  0.001  1.000`).
* `models/S001/GERASIM_406_inkl/*.las` (63 файла) — только траектория
  (`DEPTH, DEVIATION, AZIMUTH, TVD`).
* Проектный граф запрашивает каналы **`PHIE`** (пористость) и **`KINT`** (проницаемость)
  (строки 79–80 и этап 7) — таких кривых в данных нет.

**Следствие:** шаг блокировки/интерполяции ГИС работает по несуществующим каналам, поэтому
кубы `PORO`/`PERM` получают фоновые значения (наблюдаемое: PORO медиана 4.9 %, PERM медиана
0.67 мД — «пласт непроницаем»), а порог физичности `[0.1, 5000]` это пропускает, потому что
смотрит только на среднее.

**Что правильно сделать (всё — ДАННЫЕ, без хардкода):**

1. Исправить сопоставление мнемоник в данных: пористость — `POROSITY` (а не `PHIE`);
   проницаемость — **в исходных LAS отсутствует**, значит её нужно либо взять из другого
   источника (керн/зависимость), либо честно зафиксировать `PERM` как `unknown`
   (правило 6), а не публиковать фон.
2. Добавить в QA/QC проверку **наличия запрошенных каналов**: если запрошенной мнемоники нет
   в LAS — гейт `G-PETRO` должен давать `failed`/`not_applicable` с формулировкой
   «канал X отсутствует в данных», а не молча строить куб из фона.
3. Только после этого — петрофизическая связь `PERM = f(PORO)` (керн/литература со статусом
   `EVIDENCE_BACKED_CANDIDATE`) и проверка `petro.perm_physical` (доля непустых, медиана,
   число уникальных значений, дисперсия против порогов из данных).



## Пункт A. Подошва от кровли (вместо независимой интерполяции)

**Как сейчас:** обе поверхности идут независимыми шагами интерполяции по отбивкам
(`horizon_interpolate_by_marker_idw`), поэтому подошва «ловит» каждую скважину локальным
экстремумом (bull's eye).

**Как должно быть (физично и без хардкода):** подошва = кровля + толщина, где толщина
берётся из данных (отбивки/атрибуты скважин), либо подошва интерполируется с трендом
по кровле. В наборе уже есть средства:

* `wells_attribute_thickness_calculation` — расчёт толщины по скважинам (в онтологии есть);
* `horizon_calculator` — вычисление поверхности (например, подошва = кровля ± толщина);
* `grid_property_calculator` — то же для свойств (уже подтверждён пробой в F-18);
* в шаблоне интерполяции есть параметры тренда (`trend_mean_using_target`,
  `use_transformed_equations_kriging` и др. — из официального руководства тНава).

**План (данные → код не меняется):**
1. В проектном графе описать толщину как данные: правило расчёта толщины по скважинам
   (`wells_attribute_thickness_calculation`) с колонками из `Welltop.txt`.
2. Построить `U1_bot` через `horizon_calculator` (или `map_2d_calculator` для карт) от
   уже построенной кровли: `bottom = top − thickness` (знак и способ — ДАННЫЕ шага).
3. Проба на живой лицензии до `probe ok=True` (правило 8).
4. Сравнение: до/после — число локальных экстремумов у скважин (см. проверку QA/QC ниже).

## Пункт B. Проницаемость от пористости (петрофизические зависимости)

**Как сейчас:** `PERM` интерполируется по ГИС (`grid_property_interpolate_by_wells_log_3d`,
канал `KINT`), но на карте почти всюду `≈0.0001` — то есть в куб попало «пустое» значение
(при том что легенда допускает до 34.6 мД). Гипотезы, которые надо проверить фактами:
* канал `KINT` пуст/не тот в LAS (тогда интерполяция кладёт фоновое значение);
* пористость `PORO` и проницаемость `PERM` не связаны петрофизической зависимостью
  (нет `PERM = f(PORO)` из керна/зависимостей), а интерполяция ГИС «размазывает» фон;
* не применён отсев по коллектору (net) — в неколлекторе проницаемость мала, но должна
  быть явно помечена как отсутствующая, а не нулевая по всему пласту.

**План (всё — ДАННЫЕ):**
1. Свидетельством `property_stats` показать фактическое распределение `PERM` и `PORO`
   (`count`, `min/max/mean`, доля непустых) — правило 6: «нет данных» ≠ «ноль».
2. Описать петрофизическую зависимость в данных: `PERM = f(PORO)` (например, по керну или
   по зависимости вида `PERM = a·(PORO)^b`, коэффициенты — из литературы/керна, не из кода),
   и применить её штатным `grid_property_calculator` (подтверждён пробой).
3. Либо, если зависимости нет в данных проекта, — явно зафиксировать `PERM` как
   «не определена» (`unknown`), а не публиковать нефизичную карту.

## Проверки QA/QC, которые нужно добавить (обе — ДАННЫЕ + реестр)

1. **`surface.well_bullseye`** — «бычьи глаза»: для каждой скважины сравнить значение
   поверхности в её ячейке с кольцом ячеек радиуса R (R — данные): если локальный экстремум
   превышает порог (данные, например в метрах или в долях от регионального тренда) —
   находка `failed` с координатами скважины. Нет данных о скважинах/сетке → `unverified`.
2. **`petro.perm_physical`** — физичность проницаемости: доля непустых ячеек и медиана
   `PERM` должны попадать в диапазон из данных (например, `PERM` не может быть одинаковой
   константой на всём пласте: проверка дисперсии/уникальных значений); значения вне
   диапазона из данных → `failed`, нет свидетельства → `unverified`.
3. Регистрация: `ontology/qa_gate_map.yaml → result_checks` (гейты `G-STRUCT`/`G-PETRO`),
   уровни — `checks.check_severity` (критичность — ДАННЫЕ), пороги — в `checks.*`.
