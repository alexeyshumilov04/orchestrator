## б. Автоматическая сборка воркфлоу без подготовленного yaml/json — ✅ выполнено (с оговоркой)

**Что было (аудит 1-й итерации):**
```
$ Test-Path core/graph_generator.py   → False
$ Test-Path core/project_generator.py → False
$ python main.py graph --field Герасимовское --pipeline-from-ontology
  → main.py: error: argument cmd: invalid choice: 'graph'
    (choose from 'preflight', 'plan', 'run', 'serve')
```

**Что стало:**
```
$ python main.py graph --field Герасимовское --pipeline-from-ontology
  → источник состава: ontology; этапов: 8; шагов: 40; функций БЕЗ шаблона: 0
  → аудит состава: {stages: 8, verified: 40, unverified: 0, candidates: 2}

$ python main.py run --field Герасимовское --execute          # pipeline_source = ontology
  → tnav.ok = true, exit 0; steps 50 / done 48, error 0, pending_template 0
  → grid_geometry 250 × 311 × 22; 5/5 ветвей ok, scored = 5, best = S004; карт 8
  → воспроизведено дважды: execute_20261009_211804 и execute_20261009_212707
```

**Оговорка (честно):** шаблон поля поставляет выбор шагов, их порядок и объектные
привязки (без них рендер терял `objects`: «cannot find object "2D-Map Tl_thick"»,
1 карта из 8); онтология отвечает за каталог, состав, валидацию и перечень
неприменимых шагов (11 функций перечисляются в `graph.ontology_extra_steps`,
режим включения — данные `workflow.ontology_extra_steps`).

`Coordinator.project_graph()` (core/coordinator.py) устроен так:
```python
graph_dir = self.cfg.path("project.graph_dir", "ontology_project")
for cand in (graph_dir / f"{field}.yaml", graph_dir / f"{field}.yml"):
    if cand.is_file():
        return yaml.safe_load(...)        # ← источник истины — РУЧНОЙ YAML
...
return {}                                  # ← нет YAML → пустой граф, прогон бессмысленен
```
То есть состав стадий, шагов, функций, объектов и маркеров берётся **только** из
`ontology_project/gerasimovskoe.yaml`. Онтология (`ontology/tnavigator_functions.csv`,
`process_catalog.csv`, `qa_gate_map.yaml`) используется для проверки/подсказок и для
QA/QC, но **не порождает пайплайн**.

**Что нужно (конкретно, источник уже есть в репозитории):**
1. перенести из `orchestrator_v7/orchestrator/core/` модули `graph_generator.py`
   (`build_draft(field, data_root, template)`) и `project_generator.py`
   (`derive_pipeline(ontology, rules_dir, templates_dir)`, `merge_with_template`);
2. вернуть в `main.py` команду `graph` (в v5 она была) и `--pipeline-from-ontology`;
3. в `Coordinator.project_graph()` добавить приоритет: если для поля нет YAML **или** в
   `config.yaml → workflow.pipeline_source: ontology` — построить черновик графа из
   каталогов онтологии + данных поля, а YAML использовать как **переопределение**
   (объекты/параметры/маркеры), а не как единственный источник;
4. критерий приёмки: `python main.py run --field <новое поле>` без заранее написанного YAML
   строит воркфлоу и выполняет его (с деградациями там, где данных не хватает).

## в. Агенты собирают воркфлоу из онтологии и выбирают методы/параметры — ⚠️ частично

**Что реально делают агенты (по данным, подтверждено тестами и прогоном):**

| Агент | Что выбирает сам | Источник данных |
|---|---|---|
| `StructureAgent` | нужен ли врез по покрытию кровли отбивками (55/58 = 95 % ≥ 80 % → врез не строится); рабочий интервал по маркерам | секция `structural:` проектного графа |
| `GridAgent` | бокс сетки из extent структурной карты, шаг, ожидаемые `nx/ny`, включать ли разломы (по умолчанию нет) | `maps` (статистика irap) + параметры шага |
| `FaciesAgent` | **метод и конкретную функцию тНава** по карте `ontology/facies_methods.yaml`, число классов, вариограмму, согласованность с сеткой | `geostat:` + данные онтологии |
| `PetrophysicsAgent` | метод интерполяции, кубы (LAS → blocked well → куб), диапазоны физичности | `petrophysics:` + `thresholds:` |
| `SaturationAgent` | способ задания контакта, контроль `S_w`/суммы/ЗСВ | `contacts:` |
| `MapsAgent` | маршрут построения каждой карты (нативный объект/фолбэк) и полноту | `checks.map_files`, `checks.map_sources` |

**Чего не хватает для полного выполнения критерия:**
* **состав** пайплайна (какие функции, в каком порядке) не выводится из онтологии — он
  прописан в YAML (см. пункт б). Агент не «собирает воркфлоу», он **параметризует** уже
  заданный состав;
* перечень допустимых методов (`checks.facies_methods`, `checks.petro_methods`) лежит в
  общем `config.yaml`, а не в онтологии/проектном графе — при расширении набора методов
  это надо будет править в двух местах;
* нет механизма **выбора оптимального** метода по критерию (сейчас метод берётся по
  данным проекта; сравнение альтернатив и выбор «оптимального» не реализованы —
  это роль ансамбля вариаций и БЗ, где накопление опыта уже есть, но решения «какой метод
  лучше по метрике» принимает человек/ансамбль, а не агент).

**Что нужно:** пункты 1–3 из раздела «б» + перенос списков разрешённых методов в
онтологию (`ontology/method_catalog.yaml`) + правило выбора метода по критерию из
`checks`/метрик (детерминированно, с опорой на БЗ `recall/suggest`).

## г. Универсальность — ⚠️ частично

**Что подтверждено:**
* в `.py` нет ни одного незадекларированного доменного значения (см. а): имя поля, маркеры,
  бокс, пороги, мнемоники, имена кубов — всё в `config.yaml` / `ontology_project/` /
  `domain/templates/` / `domain/ontology_rules/` / `ontology/`;
* пороги проверок — данные (`checks.*`), диапазоны физичности — данные (`thresholds:`),
  допустимые методы — данные, имена объектов и кубов — данные, координаты — из
  структурной карты поля;
* аудит хардкода — автоматический тест, который **валит сборку** при появлении нового
  доменного значения в коде (кроме явно задекларированного долга).

**Почему всё равно «частично»:**
1. Новый объект сейчас нельзя запустить «как есть»: нужен **вручную написанный** проектный
   граф (состав пайплайна, объекты, маркеры, вариации). Это прямо противоречит формуле
   «универсальный, работает на любых объектах».
2. `checks.map_files`, `checks.map_kinds` и `project.stoiip_candidates` — глобальные данные
   `config.yaml`, а не часть проектного графа поля: на другом объекте с другим набором
   кубов их придётся править в конфиге (это данные, но не «поля»).
3. Встроенные проверки блока 04 привязаны к сценарию «один резервуар» (`reservoir_horizon`,
   один интервал), что для многопластового объекта потребует расширения данных.
4. Ряд проверок/шагов требует данных, которых на новом объекте может не быть (керн, SCAL,
   сейсмика) — эти шаги должны деградировать (и деградируют: `skipped_by_policy`,
   `not_applicable`), но состав пайплайна под это автоматически не перестраивается.

**Что нужно для полной универсальности:**
* пункты 1–3 раздела «б» (граф поля выводится из онтологии и данных);
* перенос `map_files`/`map_kinds`/`stoiip_candidates`/`package_blocks` в проектный граф
  либо в онтологию (единый источник на объект);
* правило «шаг без данных не исполняется и фиксирует `needs_data`» уже есть
  (`core/planner.py`) — но перечень шагов всё ещё задаётся вручную; после пункта «б»
  это станет автоматическим.
