## 3. Созданные модули

| Модуль | Что считает | Ключевой API |
|---|---|---|
| `domain/petrofacies_data.py` | **данные-контракт**: сборка правил из файлов онтологии (секция `sources`), роли колонок → имена (из `columns`), бланки (LAS + sentinel GeoMate), порог достаточности, лестница источников, ограничения k-φ, масштаб пористости | `load_rules`, `blank_values`/`is_blank`/`clean_number`, `pick_column`/`row_value`, `min_pairs`, `source_ladder`, `constraints`, `scale_porosity` |
| `domain/petrophysics_fit.py` | подгонка `log10(k)=a·φ+b` **по литотипам** + `r2`/`n_pairs`/статус источника; применение к пористости (подготовка куба K); cut-off по меченому керну | `fit_from_rows`, `fit_pairs`, `apply_fit`, `cutoff_from_labelled_core`, `FitResult` |
| `domain/facies_model.py` | порядок классов из данных, доли по скважинам, агрегаты по кубу кодов (доли, **связность**, **число тел**, NTG по ролям), параметры шага фаций, проверки интервалов | `class_order`, `connectivity_stats`, `proportions_from_wells`, `aggregate_facies`, `facies_step_parameters`, `validate_intervals` |

Модули **не вызывают тНавигатор** (проверяется тестом): это чистые расчёты по
данным; запись кубов/карт выполняет агент/раннер подтверждёнными функциями тНава.

### Пример на реальных данных поля (без лицензии)

```
python tools/petrofacies_report.py --field Герасимовское --limit 40
онтология: petrophysics_rules.yaml, geomate_reuse_rules.yaml, facies_methods.yaml, petrofacies_methods.yaml
LAS: .../data/Герасимовское/Source/RIGIS — файлов 40, со кодами фаций 40
фации: статус ok, классов 5
  код 0: доля 0.002
  код 1: доля 0.231
  код 2: доля 0.578
  код 3: доля 0.096
  код 8: доля 0.094
  net-to-gross: unknown, скважин 40
  unknown: карта ролей «код → коллектор/нет» не передана — NTG = unknown (правило 6)
```

С картой ролей (`--roles "1=reservoir,2=barrier"`) NTG становится `unknown` с
перечнем кодов без роли — то есть **не выдаётся за посчитанный**. Коды
`{0,1,2,3,8}` совпадают с составом литологии поля из проб тНава (B4_facies).

## 4. Данные онтологии (единственное место правил)

`ontology/petrofacies_methods.yaml` (новый файл, ничего существующего не переписано):

* `sources` — сшивка правил: `petrophysics_rules.yaml` (порог достаточности,
  лестница источников), `geomate_reuse_rules.yaml` (контракты и бланк),
  `facies_methods.yaml` (порог скважин, источник пропорций), сам файл (параметры
  алгоритмов). **Порог `min_pairs` не дублируется** — живёт в одном месте;
* `columns` — роль → имена колонок (мнемоники поля в коде отсутствуют);
* `interval_fields` — роль → ключ интервала (контракт GeoMate как данные);
* `blank_handling` — допуск сравнения с бланком и дополнения поля;
* `porosity_scale` — автоприведение процентов к долям;
* `rock_typing` — единая k-φ запрещена (`pooled_allowed: false`), метка
  неклассифицированных проб;
* `permeability_fit` — `transform: log10`, `r2_min: 0.70` (источник — QA/QC
  чеклист `QC_PERM_001`), защита от экстраполяции;
* `cutoff` — метод, метки классов, минимальное число наблюдений в классе,
  `provenance` (инженерный допуск прототипа — **не** литературный факт);
* `facies_model` — порядок классов, соседство и его допустимые значения,
  минимальный размер тела, предел объёма расчёта связности, роль «коллектор»,
  `patch_codes` (**пусто** до успешной пробы тНава — правило 8);
* `transfer` — реестр «взято/доработано/осталось» с проверяемыми ссылками;
* `study_sufficiency` — веса индекса изученности из GeoMate (как данные);
* `checks` — проверки, которые модули отдают в QA/QC.

Что покрыто тестами (правила 1, 6, 8):

* пороги/бланки/роли колонок/соседство/порядок классов приходят **из данных** —
  тест меняет значение в копии правил и проверяет, что результат меняется;
* пустые данные → `unknown`/`not_applicable`, коэффициенты и доли не выдумываются;

  проницаемость не логируется;
* единая k-φ не строится (ограничение `RULE_LIT_PETRO_110` из онтологии);
* cut-off без меток/при малом числе наблюдений → `unknown` без числа;
* параметры тНава патчатся только при наличии кода в шаблоне функции;
* реестр переноса закрывает **каждый** пробел `missing_to_implement`.

Регламент (полная батарея + preflight + dry-run по двум полям) выполняется
после каждой правки; результаты — в отчёте задачи.

## 6. Чего не хватает в тНавигаторе (наши модули vs функции тНава)

| Потребность | Реализуем сами (сделано) | Требует тНава |
|---|---|---|
| Связь k = f(φ) | да: подгонка по литотипам, `r2`, `n_pairs`, статус источника | запись куба K (`grid_property_calculator`) — вызов агента/раннера |
| Физичность и обоснование cut-off | да: порог по меченому керну | — |
| Подготовка параметров фациального шага | да: доли/связность/тела/порядок классов + патч по шаблону | сам вызов фациального моделирования (`grid_property_facies_modeling` / `grid_property_create_by_zones`) не подтверждён пробой на 26.2 (F-21) |
| Дискретный куб фаций | нет (наш модуль считает агрегаты) | создание дискретного свойства и **дискретной палитры** доступно только средствами тНава |
| Карты фаций/свойств | нет | `map_2d_create_by_grid_property` + экспорт; рендер PNG локальный (`domain/map_render.py`) |
| Насыщение (Sw, концевые точки, J-функция) | нет — следующий срез | нужны SCAL-данные; вызовов тНава для этого не требуется, требуется **модуль** |
| Учёт фаций/зон при интерполяции петрофизики | нет | беззонная форма подтверждена, зонная — нет (`PetrophysicsAgent._zone_decision`) |
| Пробники значений из проекта (свойства, статистики, blocked wells) | нет | API тНава (`domain/qc/probes.py`, зона petro) |

**Границы честности.** Модули не подставляют коэффициенты без керна, не считают
NTG без карты ролей, не патчат параметры тНава без подтверждённого кода в
шаблоне и не объявляют успех там, где данных нет (правило 6). Коды параметров
шага фаций остаются пустыми в онтологии до успешной пробы на лицензии (правило 8).
