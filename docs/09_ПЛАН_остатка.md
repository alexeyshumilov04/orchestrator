## Пункт 2. Агентная селекция состава онтологического вывода (критерии «в» и «г»)

**Где сейчас:** `Coordinator._reconcile_order` исключает 11 «лишних» шагов онтологического вывода
по флагу данных `workflow.ontology_extra_steps: skip|include` (при `include` они идут отдельной
стадией в конце, при `skip` — перечисляются в `graph.ontology_extra_steps`).

**Что нужно:** применимость каждого лишнего шага решает **агент-владелец** по своему решению и
базе знаний, а не флаг.

**Данные (новый файл, правило 1):** `ontology/ontology_extra_rules.yaml`

```yaml
# Применимость шагов, которых нет в выверенном составе поля (ДАННЫЕ).
# Владелец решает по своему решению: шаг включается, только если решение включено.
steps:
  map_2d_interpolate:                 {gate: G-STRUCT,  decision_key: enabled}
  map_2d_distance_to_marker:          {gate: G-STRUCT,  decision_key: enabled}
  map_2d_thickness_map:               {gate: G-STRUCT,  decision_key: enabled}
  horizon_calculator:                 {gate: G-STRUCT,  decision_key: enabled}
  create_screenshot:                  {gate: G-MAPS,    decision_key: enabled}
  grid_property_create_by_values:     {gate: G-PETRO,   decision_key: enabled}
  grid_property_create_by_zones:      {gate: G-PETRO,   decision_key: enabled}
  grid_property_interpolate_by_blocked_wells_trivial_3d: {gate: G-PETRO, decision_key: enabled}
  grid_3d_create_by_horizons_with_faults: {gate: G-GRID, decision_key: enabled}
  wells_attribute_thickness_calculation:  {gate: G-DATA, decision_key: enabled}
  map_2d_import_ascii_format:         {gate: G-DATA,    decision_key: enabled}
# Функция без правила → НЕ включается, причина пишется в отчёт (неизвестное != ложь).
```

**Точки правки (минимальные):**
1. `Coordinator._reconcile_order` — при `workflow.ontology_extra_steps: "agent"` включать лишние
   шаги стадией в конце (как при `include`) и складывать список правил в `graph["ontology_extra_rules"]`.
2. `StageRunner.run_staged` — при рендере последней стадии добавлять в `skip_functions` те лишние
   шаги, чей агент-владелец **не** включён (`decisions_by_gate[gate]["enabled"] is not True`),
   с собственной причиной в `skip_reasons`: «шаг из онтологического вывода: агент <gate> не включён».
   Решение «включён/не включён» берётся из уже существующих решений агентов — новой доменной логики
   в коде не появляется.
3. Отчёт: в стадии — `skipped_steps` (уже есть) и `ontology_extra_decisions: [{function, gate, enabled, reason}]`.

**Приёмка пункта:** (а) `main.py graph --pipeline-from-ontology` печатает решения по каждому лишнему
шагу; (б) dry-run в режиме `agent` зелёный (`error 0`, `pending_template 0`, `render_warnings []`);
(в) живой `--execute` даёт те же 8 карт, 5/5 ветвей и `tnav.ok = true`; (г) тесты: с выключенным
решением владельца шаг пропускается с причиной, с включённым — исполняется.

## Пункт 3. Невязка карты метрики с табличным агрегатом — оформить как `unknown` (правило 6)

**Факт:** карта метрики строится из вычисленного свойства (`HCPV / Bo`), её сумма 1,709e8,
тогда как табличный агрегат `vol.stoiip` = 2,039e8 — расхождение около 16 % (иные Sw/Bo/зоны в
таблице волюметрии). Сейчас это расхождение нигде не отражено: карта `passed`, агрегат `passed`.

**Что нужно:** проверка-свидетельство, которая сравнивает эти две величины и при превышении
допуска даёт `unknown` (не «прошло» и не «провал»), с причиной и обеими величинами.

**Данные:** `checks.metric_vs_table_tolerance: 0.05` (допуск 5 %), плюс зарегистрировать проверку
в `ontology/qa_gate_map.yaml → result_checks.G-VOL`.

**Реализация:** пробник отдаёт `map_sum` (сумма непустых ячеек выгрузки карты метрики) и уже
отдаёт агрегат; проверка сравнивает относительное расхождение с допуском из данных:
`|map_sum - table| / table <= tolerance` → `passed`; иначе `unknown` с формулировкой
«карта метрики — производная величина (HCPV/Bo), таблица считает запасы с иными Sw/Bo/зонами:
расхождение N % требует согласования допуска или формулы». Если одной из величин нет →
`unverified` (свидетельства нет).

**Приёмка пункта:** тесты на три состояния (в допуске → `passed`; вне допуска → `unknown`;
нет одной из величин → `unverified`); живой прогон показывает `unknown` с числами, а не «прошло».

## Пункт 2а (F-27) — ЗАКРЫТ: вывод онтологии подменял проверенные данные поля

**Причина (найдена):** `graph_from_ontology` возвращал граф, в котором вывод онтологии
перекрывал явные данные поля: `build_draft` дописывает свои ключи (`markers.candidates`,
`markers_candidates` и др.), и они подменяли проверенный `markers` поля — из-за этого
структурный отчёт терял отбивки (`wells_with_top: 0` из 58).

**Исправление:** явные данные поля СИЛЬНЕЕ вывода онтологии — после согласования
порядка все ключи шаблона восстанавливаются поверх вывода онтологии (кроме
согласованного `pipeline`).

**Проверено:** в режиме `ontology` — `test_structural_agent` **69/0** (было 69/1),
`test_agents` 223/0, `test_ontology_extra_selection` 11/0; полный регламент — **0 красных
файлов**, dry-run 50 шагов / done 48 / `error 0` / `pending_template 0` / `render_warnings []`,
`preflight: OK`. Режим `ontology` переведён в **умолчание** и подтверждён ранее тремя
живыми прогонами (`tnav.ok = true`, 8 карт, 5/5 ветвей, `scored = 5`, `best = S004`).

**Что отвергнуто по пути (для истории):** гипотеза о входных путях (`dataset_root`, `inputs`
идентичны), гипотеза о составе/воркфлоу (32 шага, 0 расхождений по `parameters`/`objects`),
гипотеза о неоднозначном сопоставлении повторов функций (правка не помогла — откачена).

**Осталось в пункте 2:** привязки 2 из 11 дополнительных шагов онтологического вывода
(помечены `verified: false` с точными ошибками тНава) — режим `agent` исполняется
агентами, но эти шаги требуют объектных привязок поля и пробы.



**Факт (проверено):** `tests/test_structural_agent.py` в режиме `pipeline_source: yaml` — **69/0**,
в режиме `ontology` — **69/1**:

```

       {'top_marker': '', 'base_marker': '', 'wells_total': 58,
        'wells_with_top': 0, 'wells_with_base': 0, 'top_coverage': None}
```

**Что уже исключено:**
* входные данные и состав совпадают: `dataset_root` = `data/Герасимовское/Source`, `inputs`
  (`Wellhead.txt`, `Welltop.txt`, `struct/depth_u1.irap`, `struct/std_depth_u1.irap`) — те же;
  `markers` сохраняются и даже обогащаются кандидатами отбивок;
* **отрендеренный воркфлоу совпадает ПОЛНОСТЬЮ**: 32 шага в обоих режимах, расхождений

* гипотеза о неоднозначном сопоставлении повторов функций проверена и **отвергнута**
  (правка не помогла, тест селекции сломался — откачена).

**Вывод:** различие НЕ в воркфлоу и не во входных данных, значит его вносит другой
потребитель `project_graph()` — то есть путь отчёта структурного агента (интервал по
отбивкам). Проверять: что именно читает структурный отчёт (`static_ev`/`well_tops`)
и какие ключи графа он использует помимо `pipeline`.

**Где искать дальше:** различие в СОДЕРЖИМОМЕ шагов после согласования
(`_reconcile_order` берёт базой шаг шаблона и дополняет его онтологическим выводом) —
вероятно, один из шагов этапов работы с отбивками получает параметр/привязку из
онтологического вывода, из-за чего маркеры не доходят до расчёта интервала.
Проверять сравнением отрендеренных шагов «отбивки/маркеры» в обоих режимах.

**Следствие:** умолчание оставлено `yaml` (проверенное), режим `ontology` включается
данными и требует закрытия F-27 — при этом приёмочные прогоны в этом режиме уже давали
полный результат (`tnav.ok=true`, 8 карт, 5/5 ветвей).
