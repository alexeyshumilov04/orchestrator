# 15. Онтология в общем виде: параметры выводятся из данных, домена в коде нет

Замечание заказчика, к которому относится этот документ: «кажется, что ты просто
перенёс YAML/JSON в онтологию, что по факту хардкод». Документ фиксирует
**машинно-проверяемый** ответ: что было доменом в коде/правилах, куда это перенесено,
и как доказано, что состав и параметры собираются из онтологии без тестовых объектов.

Проверки: `tests/test_ontology_generality.py` (25), `tests/test_no_domain_in_code.py`
(6, включая КОММЕНТАРИИ), `tests/test_verify_hardcode.py` (независимый аудит),
команда отчёта — `python main.py audit --generality` (JSON) или
`python tools/audit_generality.py [--no-probe] [--out …]`.

## 1. Находки независимого аудита (было 8) — как закрыты

| Было (test_verify_hardcode) | Классификация | Что сделано |
|---|---|---|

| `core/pipeline.py:77`, `core/runner.py:65` литерал `"percent"` | не домен: ключ протокола прогресса JSON | то же исключение (единица измерения ≠ имя объекта) |

## 2. Домен, вычищенный из КОДА (сверх 8 находок)

Аудит общности сканирует литералы, ИМЕНА и КОММЕНТАРИИ рантайм-кода
(`core/`, `agents/`, `domain/`, `tools/`, `main.py`, `api.py`).

| Файл | Было | Стало |
|---|---|---|
| `core/coordinator.py` | литералы `main_grid` (fallback имени сетки), `_STOIIP_TMP`, комментарии с именами кубов/маркеров/карт | имя сетки — `project.grid_name` (ДАННЫЕ), не задано → сниппет не строится (unknown); временный файл метрики — `_METRIC_TMP`; комментарии домен-нейтральны |
| `core/ensemble.py` | `Scenario(id="S001")`, метки «базовая ГМ» | id/метка базовой ветки — параметры (`ensemble.default_variant` в данных); нет данных → пул пуст (правило 6) |
| `core/datasets.py` | `_PREFERRED_SURFACE = ("depth_u1.irap", …)` — прямые имена файлов поля | маски предпочтений — ДАННЫЕ `input_recognition_rules.preferred_names` (генерические маски), нет правила → первый кандидат |
| `core/coordinator.py` | имя объекта границы модели (`Boundary`) | имя берётся из объектов шагов графа по ролям `object_binding_rules.boundary_name_roles`; не найдено → контур не пишется |
| `agents/runner.py` | `range_vals["PORO"] = ev["poro_mean"]` | код параметра и ключ свидетельства — из `checks.properties.<роль>.{cube, mean_key}` |
| `domain/geostat.py` | кортежи мнемоник `PHIE/PORO/KINT/PERM/LIT/FACIES/…` | мнемоники — ПАРАМЕТР вызывающей стороны (`curve_mnemonics`), в коде имён кривых нет; не заданы → выборка не собирается |
| `domain/welltops.py` | `_RESERVOIR_MARKER_TOKENS = ("BAJ","J1","J2","J3")` | мнемоники кровли — параметр (`reservoir_marker_tokens`, из данных поля); не заданы → оценка кровли не выдаётся |
| `tools/check_surface_bullseye.py` | `run_dir / "Wellhead.txt"` | таблица устьев ищется по ролям/маскам данных (`core.datasets.resolve_inputs`); не найдена → понятная ошибка с `--wells` |
| `main.py`, `core/graph_generator.py`, `domain/trajectories.py`, `domain/qc/probes.py` | комментарии/докстроки с именами файлов, кубов и маркеров поля | текст домен-нейтрален (смысл сохранён) |

Мёртвый долг правила 1 в коде **вычищен полностью**: `audit --generality` показывает
`code_declared_debt: 0`. Позиции в `config.yaml: hardcode_audit.known_debt` стали
«мёртвыми» (их больше нет в файлах) — их следует удалить из `config.yaml`
(файл вне зоны этой задачи; независимый аудит печатает их как `[WARN] мёртвый долг`).

## 3. Онтология без параметров объектов тестирования

Проверяются файлы правил из перечня `ontology/generic_vocabulary.yaml: audited_rule_files`
(12 файлов). Найдено и исправлено:

| Файл правил | Было (параметр объекта) | Стало (правило) |
|---|---|---|
| `input_recognition_rules.yaml` | `patterns: ["RIGIS", …]` — имя каталога поля; комментарии с файлами/маркерами поля; секция `acceptance_example` с именем тестового поля и его файлами | роль ГИС распознаётся по СОДЕРЖИМОМУ (`.las` + `file_masks`); комментарии обезличены; `acceptance_example` удалён (пример перенесён в документацию) |
| `facies_methods.yaml` | `palette.name: "FACIES"` — имя свойства поля | `name: "__RESULT_PROPERTY__"` + `name_from: "result_grid_property"`: имя подставляет рендер из ДАННЫХ поля |
| `petrophysics_rules.yaml` | комментарии с мнемониками и число значений кривой; текст `output` со ссылкой на имя куба | домен-нейтральные формулировки (пороги/правила сохранены) |
| `object_binding_rules.yaml` | комментарий с именами демо-объектов | формулировка без имён; добавлены `boundary_name_roles` (роли → имя объекта границы) |
| `thresholds_rules.yaml`, `structural_geostat_rules.yaml`, `pvt_scal_rules.yaml`, `ensemble_rules.yaml`, `ontology_extra_rules.yaml`, `geomate_reuse_rules.yaml`, `petrofacies_methods.yaml`, `qa_gate_map.yaml` | — | параметров объектов нет (проверено машинно) |

Новое правило разделения: **значения** файлов правил проверяются на имена объектов,
**ключи** — идентификаторы схемы (роли, аргументы функций, политики) и допустимы
правилом 1; они выводятся отдельным списком `schema_key_advisory`.

## 4. Доказательство автоматической сборки (без тестовых объектов)

Команда: `python main.py audit --generality` (в отчёте — блок `generality_proof`).
Доказательство состоит из двух прогонов, где данные тестового объекта НЕ участвуют:

1. **Поле без файла в `ontology_project`.** Каталог `project.graph_dir` подменяется
   пустым временным; вызов `Coordinator.graph_from_ontology(поле, template={})`:

   ```
   поле без файла      → источник ontology, этапов 8, шагов 40, функций 40
   поле с минимальным  → этапов 8; ролей из онтологии 7, форматов 8,
   файлом данных          требований шагов к объектам 14; правок кода 0
   ```

2. **Поле с МИНИМАЛЬНЫМ файлом данных** — только `field` и `dataset_root`:
   состав, роли, форматы и требования к объектам те же, потому что выводятся из
   онтологии; из файла данных берутся ровно его ключи.

Дополнительно в отчёте фиксируются параметры, выведенные из онтологии:
`petrophysics` (бланки, политика, `scale_from_data`, лестница источников k-φ,
ограничения) и `structural` (метод базовой поверхности, порог вреза, QC «бычьих
глаз», тип вариограммы).

**Как добавить новое поле (только данные):**
1. каталог набора данных: `data/<поле>/Source/…`;
2. файл поля `ontology_project/<поле>.yaml` — значения: входы, маркеры, кубы,
   контакты, PVT/SCAL, пороги, вариации (структуру можно скопировать у существующего
   поля: состав шагов всё равно выводится из онтологии);
3. при необходимости — запись роли в данные распознавания (`roles`/`formats`) и
   предпочтения имён (`preferred_names`), если у поля непривычные имена файлов.
   Правок кода не требуется; доказательство — п. 4.

## 5. Как это проверяется машинно

| Инструмент | Что проверяет |
|---|---|
| `core/generality_audit.py` | реестр поля ИЗ ДАННЫХ; сканы кода (литералы/имена/комментарии/docstring) и файлов правил; доказательство сборки; классификация `violation/declared_debt/allowed` |
| `tools/audit_generality.py`, `main.py audit --generality` | тот же отчёт как команда (JSON + краткая сводка), код возврата 1 при нарушениях |
| `tests/test_ontology_generality.py` | 25 проверок: реестр, отсутствие домена в коде, отсутствие параметров объектов в правилах, доказательство сборки, обоснованность исключений |
| `tests/test_no_domain_in_code.py` | официальный аудит: литералы, имена и **комментарии**; генерическая лексика исключается по данным с обоснованием; исключения — из `config.yaml` |
| `tests/test_verify_hardcode.py` | независимый аудит: широкий набор токенов, `domain/qaqc/**`, мёртвый долг, пороги в коде |

Генерическая лексика (`ontology/generic_vocabulary.yaml`) — единственный класс
исключений, добавляемый этой задачей; правила пользования: только единицы измерения
и стандартные термины API/протокола, каждая позиция с `why`, исключение действует
только для значения из ключа-носителя единиц (`*.units`), неиспользованные позиции
видны в выводе (мёртвых исключений быть не должно).

## 6. Что осталось (честно)

* **`config.yaml: hardcode_audit.known_debt`** — 22 позиции стали мёртвыми после
  вычистки кода; удалить их (файл вне зоны задачи) — иначе независимый аудит
  продолжит печатать `[WARN] мёртвый долг`.
* **Docstring-и** (21 вхождение) — документация: считаются отдельно и в вердикт не
  входят (та же конвенция, что в официальном тесте и у верификатора). При желании
  доводятся до полной домен-нейтральности.
* **`tools/probe_*.py`** — протоколы проб на живой лицензии: имя объекта здесь
  ПРЕДМЕТ измерения (аналог теста), файлы исключены из скана по данным
  (`scan_exclusions`, с обоснованием).
* **`domain/templates/*.txt`** — сырые шаблоны функций тНава (выгрузка), содержат
  имена демо-проекта; это ДАННЫЕ, рендер заменяет их привязками поля
  (`template_demo_names` — перечень для контроля «протечек»).
