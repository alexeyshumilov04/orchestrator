# 16. Насыщение по J-функции/SCAL: модуль, правила, интеграция

Срез после [15_ОНТОЛОГИЯ_общий_вид.md](15_ОНТОЛОГИЯ_общий_вид.md). Закрывает позицию
`petro.saturation_model` из реестра переноса GeoMate: в GeoMate насыщение считалось
только по Арчи из диалога (Rw/Rt ползунками), ни SCAL, ни J-функции не было.

Проверки: `tests/test_saturation_model.py` (46), полная батарея включая
`tests/test_verify_*.py`, `preflight`, dry-run двух полей.

---

## 1. Что создано

| Файл | Что делает |
|---|---|
| `domain/saturation_model.py` | J(Sw) = (Pc/(σ·cosθ))·√(k/φ); подгонка `J = A·Sw^(−B)` лог-линейно **по типам породы** с `r2`, `n`; концевые точки (Sw_irr/Sw_max) по данным; обращение `sw_from_j` для модели по высоте; приём матриц SCAL поля (`swof`/`sgof`) |
| `ontology/petrofacies_methods.yaml: saturation` | все правила и контракт: роли колонок, матрицы→роли, формула и источники J, пороги достаточности/r2, концевые точки, критерии применимости |
| `agents/saturation.py` | вызов модуля (`scal_model` в решении): статус, концевые точки, источник правила и статус знания; пробелы — в `unknown` |
| `agents/petrophysics.py` | вызов `domain/petrophysics_fit.py` (`permeability_fit` в решении): путь к таблице керна — данные поля, правила — онтология |

Статусы результата: `ok`, `low_r2` (связь есть, качество под флагом), `insufficient`
(мало точек / нет σ·θ / нет k·φ по правилу), `degenerate`, `no_data`,
`not_applicable` (SCAL-данных нет). Ни одно число не выдумывается (правило 6).

## 2. Правила насыщения в онтологии — с provenance

| Ключ | Значение | Источник (provenance) |
|---|---|---|
| `j_function.formula` | `(pc / (sigma * cos(theta))) * sqrt(k / phi)` | `RULE_LIT_PETRO_060`, `LIT-0625#p15` (Акиньшин/Кантемиров, практическое руководство по ГИС): пересчёт капиллярных кривых с учётом σ и cos θ |
| `j_function.normalisation` | `sqrt_k_over_phi`, альтернатива `pc_over_sigma` | нормировка по пористости/проницаемости; альтернатива — только как **кандидат** (`candidate`), не факт |
| `j_function.theta_units` | `deg` | единицы угла обязательны: без них J не строится (`insufficient`) |
| `j_function.unit_scales` | `pc/sigma/permeability = 1.0` | множители ДАННЫХ поля; нет множителя → 1.0 **и** признак `units_assumed`, а не молчаливое «сошлось» |
| `fit.form` / `transform` | `J = A·Sw^(−B)`, `log10` | `RULE_LIT_PETRO_070`, `LIT-0199#p15` (Modern Reservoir Simulation): насыщенность по высоте через капиллярное давление |
| `fit.min_pairs = 10`, `r2_min = 0.70` | пороги | `min_pairs` — **engineering_default** (прототип, помечено в данных); `r2_min` — критерий QA/QC `QC_PERM_001` |
| `fit.pooled_allowed = false` | типизация обязательна | `RULE_LIT_PETRO_110` (единая зависимость недопустима при литолого-фациальной изменчивости) |
| `end_points` | Sw_irr = min, Sw_max = max, `min_samples = 5` | `RULE_LIT_SCAL_010` (концевые точки по керну/SCAL, **не константой**); `knowledge_status: REQUIRES_SOURCE` — provenance самого правила в `pvt_scal_rules.yaml` = `pending` |
| `tables` | `swof → [sw, krw, kro, pc]`, `sgof → [sg, krg, krog, pc]` | соответствие матриц поля ролям — данные; мнемоник в коде нет (правило 1) |
| `knowledge_status` | `EVIDENCE_BACKED_CANDIDATE` | J-функция и её форма подкреплены литературой индекса, но требуют проверки на керне поля |

## 3. Что показали данные поля (честный результат)

В проектном графе есть только матрицы ОФП `scal.swof`/`scal.sgof` (3 строки каждая),
без σ, θ, k, φ и без таблицы капиллярометрии:

```
from_project_scal(...) → status insufficient
  j_fit: insufficient (нет колонок σ/θ → J не строится; причина перечисляет
         кандидатов имён из онтологии)
  end_points: insufficient (3 наблюдения < min_samples 5 → значения НЕ публикуются)
```

То есть модуль **готов к SCAL**, но по фактическим данным поля выдаёт `insufficient`
с причинами, а не «посчитанную» насыщенность. Это правильный результат правила 6:
чтобы получить J(Sw) и концевые точки, нужны данные капиллярометрии (Pc, Sw, σ, θ) и
пара φ/k по образцам — их в поле пока нет.

Интеграция в решениях агентов (приёмка не затронута):

* `SaturationAgent.decide(...)` → ключ `scal_model` (статус, концевые точки,
  `source_rule`, `knowledge_status`), пробелы SCAL — в `unknown`;
* `PetrophysicsAgent.decide(...)` → ключ `permeability_fit`; путь к таблице керна —
  `petrophysics.core_data` в данных поля. Нет пути → `not_applicable` с причиной;
  есть CSV → подгонка по литотипам (`ok`, коэффициенты из керна).

## 4. Как подключается реальный SCAL

1. Положить таблицу капиллярометрии в набор данных поля (CSV/TXT) и указать путь в
   данных поля; роли колонок (`pc`, `sw`, `sigma`, `theta`, `permeability`,
   `porosity`, `rock_type`) уже описаны в онтологии, добавлять кандидаты имён —
   только данные;
2. либо заполнить матрицы графа `scal.<имя>` так, чтобы в них были роли из
   `saturation.tables`; при наличии Pc и σ/θ в матрицах подгонка пойдёт автоматически;
3. пороги достаточности/`r2` — заменить проектным критерием (помечены как
   инженерный допуск прототипа);
4. запись куба Sw в проект тНава выполняет агент/раннер подтверждёнными функциями —
   модуль только считает зависимость.

## 5. Осталось (почему)

* **Реальные данные SCAL/капиллярометрии** — в поле отсутствуют; без них J(Sw) и
  концевые точки остаются `insufficient` (правило 6), проверить на факте нельзя;
* **Sw по высоте (saturation height function)** — обращение `sw_from_j` реализовано,
  но связка «высота над контактом → Pc → Sw» с контактами/плотностями флюидов требует
  данных PVT/контактов (контакт в поле есть через `contacts`, плотности — в `pvt`);
  следующий срез при появлении керна;
* **Запись куба Sw** — функция тНава (агент/раннер), модуль её не вызывает;
* `min_pairs`/`min_samples` — инженерные допуски прототипа (помечены в данных),
  заменяются проектным критерием достаточности.
