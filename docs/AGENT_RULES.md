## 1. ПРАВИЛО 1 — ДОМЕН ТОЛЬКО В ДАННЫХ

Имена объектов, маркеров, кубов, порогов, путей, координат живут **только** в
`config.yaml`, `ontology_project/*.yaml`, `domain/templates/`, `domain/ontology_rules/`, `ontology/`.
В `.py` — **ни одного** такого значения: только **ключи** данных.

Контроль автоматический: `tests/test_no_domain_in_code.py` собирает список запрещённых
токенов ИЗ ДАННЫХ (ключи проектного YAML, `workflow.foreign_tokens`) и разбирает код через
`ast` (комментарии/docstring-и не считаются; идентификаторы — по сегментам имени).
Исключения (`hardcode_audit.allow`) и **известный долг** (`hardcode_audit.known_debt`) —
тоже данные; долг виден в отчёте теста и должен стремиться к нулю.

Допустимо в коде: **идентификаторы СХЕМЫ** (тип объекта `Grid3d`, `Map2d`; id гейта
`G-FACIES`; профиль BDI `AG_FACIES`) — они перечислены в `hardcode_audit.allow` с причиной.

## 2. ПРАВИЛО 2 — НОВАЯ ФУНКЦИЯ тНава = ТРИАДА

1. `domain/templates/<function>.txt` — **сырой** шаблон из эталонного воркфлоу v26.1/v26.2
   (не выдуманный: источник указывается в комментарии шаблона);
2. `domain/ontology_rules/<function>.rdf` — правило (параметры, входные/выходные объекты,
   `шаблон_кода`);
3. блок в `ontology_project/<поле>.yaml`: `stage → function → parameters/objects/replace`.

Нет хотя бы одного элемента — шаг помечается `pending_template` и в прогон не идёт.

## 3. ПРАВИЛО 3 — ПРОВЕРКА ПОСЛЕ КАЖДОЙ ПРАВКИ

После **каждой** правки прогоняются (в этом порядке):
`test_v5` (32/32) → `test_agents` (223/223) → `test_base_agent` (37/37) →
`test_no_domain_in_code` → `main.py preflight` → `main.py run --field Герасимовское` (dry-run).

**Инварианты dry-run** (число шагов НЕ инвариант — оно растёт с каждой новой триадой):

| Инвариант | Значение |
|---|---|
| `steps.error` | `0` |
| `render_warnings` | `[]` |
| `steps.pending_template` | `0` (у каждой функции есть шаблон + правило) |
| `steps.done` | `steps.total − steps.counts.skipped_by_policy` (штатный skip ровно один — шаг вреза) |
| историческая точка отсчёта | `steps.total = 36` на момент создания `orchestrator_v8/` (до этапа E5) |

Свой дельта-вклад в `steps.total` каждый участник фиксирует в отчёте числом.

Если какую-то проверку уронить нельзя по объективной причине — она фиксируется в отчёте
как **деградация с причиной**, а не «подчищается» числом.

## 4. ПРАВИЛО 4 — МОДЕЛЬ В ОТМЕТКАХ: ПОРЯДОК ГОРИЗОНТОВ bottom-first

В `horizons_table` горизонты перечисляются **снизу вверх** (подошва → кровля). Модель в
отметках (Z < 0). Иначе тНав даёт нулевые толщины и `The resulting grid has no elements!`.

## 5. ПРАВИЛО 5 — ПРОГОН ВСЕГДА С ЧИСТОГО ПРОЕКТА

Старый `.snp/.snf` удаляется перед прогоном (иначе в проекте остаётся `main_grid`
прошлого прогона и шаг сетки падает). `models/` и `runs/` создаются заново.

## 6. ПРАВИЛО 6 — НЕИЗВЕСТНОЕ ≠ ЛОЖЬ

* QA/QC-проверка без входных данных → `not_applicable` (модель **не** штрафуется);
* правило, не формализованное в коде/данных → `unknown` (не `false`);
* агент без входов → режим `ABSTAIN`, перечень `missing`; план не выдумывается;
* отсутствие данных **никогда** не подменяется нулём/константой/«прошло».

## 7. ПРАВИЛО 7 — ЧУЖИЕ ЗОНЫ/РЕГИОНЫ/КУБЫ ОТКЛЮЧАТЬ

В шаблонах, снятых с обучающих проектов, есть большие вложенные структуры чужого проекта
(`Litho3D`, `zone_id`, `Facies3D`, `CS_trend`, `Res3D`, `paleo_Litho`, бокс `2221900`…):
их надо гасить — `use_zone=False`, `use_region=False`, пустые `find_object`, `replace` имён.
Список чужих токенов — данные `workflow.foreign_tokens`; проверка — `contract.foreign_tokens`.

Исключение, проверенное реальным прогоном (`docs/tasks/B3_petrophysics.md`):
для интерполяции по объёму нужна «беззонная форма» —
`ZoneRegionFilter(zone=None)` + `ZoneRegionParameters(use=True, zone=None)`.

## 8. ПРАВИЛО 8 — ПРОВЕРЯЙ ФАКТЫ ПО ЭТАЛОНУ, НЕ ВЫДУМЫВАЙ

Источники в порядке достоверности:
1. `domain/ontology_rules/reference_workflow.py` + `domain/templates/*.txt` (машинный эталон v26.1,
   `v0_0_300a`) — **абсолютный** приоритет;
2. `orchestrator_v7/orchestrator/docs/tasks/B3_petrophysics.md`, `B4_facies.md`,
   `tools/probe_facies_modeling.py` — протоколы реальных прогонов (что падало и почему);
3. `.py`-файлы курсов «Примеры работы» — **низкая** достоверность (api v0.0.38…v0_0_321,
   ни один не сгенерирован v26.1);
4. `ontology/tnavigator_functions.csv` (3257 функций) — номенклатура и страница мануала,
   **без сигнатур**; сигнатура = «не найдено», пока не подтверждена пробой на живой лицензии.

Ничего не «достраивать по смыслу»: если сигнатура/схема не найдена — писать
«не найдено» и оформлять как открытый вопрос, а не как рабочий вызов.

## 9. Регламент работы команды

1. **Одна правка — один смысл.** Перед правкой: найти, где задача уже решена
   (поиск по имени функции тНава и по стадии), и сделать **минимальную** правку.
2. **Области записи не пересекаются.** Каждый участник пишет только в свои файлы
   (см. задание). Общие «конфликтные» файлы (`config.yaml`,
   `ontology_project/gerasimovskoe.yaml`, `core/coordinator.py`, `agents/runner.py`)
   правит либо Lead, либо назначенный владелец — по одному в момент времени.
3. **Триада + тест.** Каждая новая функция тНава приходит с шаблоном, правилом,
   блоком YAML и (если применимо) проверкой в `tests/`.
4. **Отчёт о работе** — короткий: что изменено (файл), что проверено (команда + вывод),
   что осталось открытым (риск/вопрос). Без «работает» без вывода команды.
5. **Провал реального прогона не скрывается**: фиксируется текст ошибки тНава, стадия,
   элемент и рабочая гипотеза. Статус «заблокировано» — нормальный результат этапа.
6. **При сомнении — спросить Lead**, а не изобретать.
