# Петрофизика должна жить в ОНТОЛОГИИ, а не в проектном графе (проверка и план)

## Замечание заказчика (раунды 84–86) и его подтверждение фактом

1. «Зависимость пористость/проницаемость обычно строится **по экспериментальным данным,
   которые есть по скважинам** — предусмотри это».
2. «КРИТИЧНО: зачем ты пишешь новые методы в проектный граф? По факту ты подгоняешь прототип
   под тестовый кейс. Это надо вносить в онтологию. **Проверь, что все методы, которые ты
   добавляешь, доступны агентам при сборке плана из онтологии** (а не из json|yaml)».

**Проверка выполнена (команды и вывод):**

```
$ python main.py graph --field Герасимовское --pipeline-from-ontology
  → источник состава: ontology; этапов: 12; шагов: 51; уникальных функций: 29

ключи петрофизики в выведенном графе: []
perm_from_poro есть: False
```

**Вывод: замечание справедливо.** Всё, что я добавил в `ontology_project/gerasimovskoe.yaml`
(единицы `expect`, бланки `null_values`, масштаб `PHIE`, зависимость `perm_from_poro`
с литературными правилами), **не попадает в план, собранный из онтологии**. Значит при работе
с новым полем (без ручного YAML) агент этих правил не увидит — это и есть «подгонка под кейс».

## Что нужно сделать (целевая архитектура)

1. **Новый файл данных онтологии** `ontology/petrophysics_rules.yaml` — единственное место
   для: обработки бланков LAS, проверки единиц и диапазонов (`expect`), масштаба кривых,
   правил построения проницаемости. Проектный YAML при этом не должен дублировать эти правила
   (там остаются только полевые значения: какие мнемоники у поля, где данные).
2. **Зависимость k-φ — ПО ЭКСПЕРИМЕНТАЛЬНЫМ ДАННЫМ СКВАЖИН.** Контракт данных:
   ```yaml
   core_phi_perm:
     source: "data/<поле>/Core"        # ДАННЫЕ: где лежат пары «пористость–проницаемость»
     format: "csv|las|table"           # формат — данные
     fit: "per_lithotype"              # обязательное условие RULE_LIT_PETRO_110:
                                       # единая k-φ недопустима, подгонка по литотипам/фациям
     transform: "log10"                # лог-линейная регрессия (обычная практика для k-φ)
     min_pairs: 30                     # порог достаточности выборки (ДАННЫЕ, не константа кода)
     fallback: "literature"            # если пар мало → литературная форма со статусом
                                       # EVIDENCE_BACKED_CANDIDATE и явным флагом needs_review
   ```
   Правило агента: **сначала керн** (подгонка по экспериментальным точкам, по литотипам),
   и только при недостатке экспериментальных данных — литературная форма, всегда со статусом
   и пометкой «требует подтверждения» (правило 8). Нет ни керна, ни литературы → `PERM`
   фиксируется как `unknown` (правило 6), а не публикуется фоном.
3. **Агент собирает это сам**: правило попадает в план из онтологии, а не из проектного YAML.
   Для этого правила читаются тем же путём, что `decision_tables`/`literature_rules_ext`
   (данные онтологии → решения агентов → шаги плана).
4. **Проверки QA/QC** (в онтологии/реестре, не в коде):
   `petro.log_units_and_range` (единицы/диапазон против `expect`, бланки исключаются),
   `petro.perm_relation_source` (откуда взята k-φ: керн / литература / unknown — с числами
   выборки), `petro.perm_physical` (медиана, доля непустых, число уникальных, дисперсия
   против порогов из данных).

## Критерий приёмки переноса (проверяемый)

```
python main.py graph --field <поле> --pipeline-from-ontology
  → в выведенном графе/решениях ПРИСУТСТВУЮТ:
      правила единиц и бланков LAS,
      правило построения проницаемости (керн → литература → unknown),
      ограничение «единая k-φ недопустима» (по литотипам)
  → и всё это на поле БЕЗ ручного ontology_project/<поле>.yaml
```

Пока этот критерий не выполнен, любые петрофизические правки в проектном YAML считаются
временными и подлежат переносу в онтологию.
